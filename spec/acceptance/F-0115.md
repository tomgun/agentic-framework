# F-0115: Git Workflow Branch Check

## Overview

Enforce git workflow policy configured in STACK.md. When `git_workflow: pull_request` is set, block commits directly to main/master branches and guide users toward proper PR workflow.

## User Story

As a developer using the framework, I want the pre-commit hook to enforce my chosen git workflow so that I don't accidentally commit directly to main when I intended to use PRs for review.

## Acceptance Criteria

### AC-001: Branch Policy Check in Pre-Commit (BLOCK)

**Given** a project with `git_workflow: pull_request` in STACK.md
**When** attempting to commit while on main or master branch
**Then** the pre-commit hook BLOCKS the commit with:
- Clear error message explaining the policy violation
- Option 1: Create a feature branch (`git checkout -b feature/description`)
- Option 2: Hotfix bypass with `git commit --no-verify`
- Option 3: Change workflow to `direct` in STACK.md

### AC-002: Direct Workflow Not Blocked

**Given** a project with `git_workflow: direct` in STACK.md
**When** committing on main or master branch
**Then** no warning or block related to branch policy

### AC-003: Feature Branch Not Blocked

**Given** a project with `git_workflow: pull_request` in STACK.md
**When** committing on a feature branch (not main/master)
**Then** no warning or block related to branch policy

### AC-004: Profile-Aware Defaults in scaffold.sh

**Given** running scaffold.sh with Core profile
**Then** STACK.md is created with `git_workflow: direct`

**Given** running scaffold.sh with Core+PM profile
**Then** STACK.md is created with `git_workflow: pull_request`

### AC-005: Core Profile Git Workflow Question

**Given** init_playbook.md guidance for Core profile
**When** initializing a Core profile project
**Then** the playbook includes a step asking the user's git workflow preference:
- Direct commits (faster, less ceremony)
- Pull Request workflow (review before merge)

### AC-006: Core+PM Profile No Question

**Given** init_playbook.md guidance for Core+PM profile
**When** initializing a Core+PM project
**Then** pull_request is set by default without asking (formal tracking = formal review)

### AC-007: STACK.template.md Documentation

**Given** STACK.template.md
**Then** it includes clear comments explaining:
- What pull_request vs direct means
- That pre-commit BLOCKS (not warns) on main with PR workflow
- How to use escape hatch for hotfixes

## Design Rationale

### Why BLOCK Instead of WARN?

- **User explicitly chose** `pull_request` workflow = they want enforcement
- **Agents ignore warnings** - they'll commit anyway
- **Policy violation, not judgment call** - branch policy is black-and-white
- **Built-in escape hatch** - `git commit --no-verify` for intentional hotfixes

### Why Ask Core Profile But Not Core+PM?

- **Core users are varied**: Some want speed (direct), some want safety (PR)
- **Core+PM implies formality**: If doing formal specs/acceptance criteria, likely want PR review too
- **Respects user choice**: Framework adapts to user preference, not the other way around

## Implementation Notes

The implementation adds check 9/9 to pre-commit-check.sh. The check:
1. Reads `git_workflow` from STACK.md
2. Gets current branch name
3. If workflow is `pull_request` AND branch is main/master → BLOCK
4. Clear message with 3 options to proceed

The check respects `--no-verify` as an intentional escape hatch for hotfixes.
