# F-0153: AC-Level Coverage Tracking — Acceptance Criteria

**Feature**: Extends coverage tracking from feature-level to individual acceptance criteria, mapping specific tests to specific ACs.

---

## Behavior (what the user needs — technology-agnostic)

When checking test coverage for a feature, the agent can see not just "feature has tests" but which specific acceptance criteria have corresponding test assertions and which don't. This surfaces undertested requirements before they become bugs. Uses naming conventions + LLM analysis for mapping — results are informational since mapping will be imperfect.

---

## Acceptance Criteria

### Core Tracking (P1 — MVP)
**Verify independently**: Run coverage tool on a feature with known test gaps
- [ ] **AC-001**: Coverage tool reports per-AC coverage status (covered/not covered) for a given feature
- [ ] **AC-002**: Test→AC mapping uses naming conventions (test file names, function names containing AC IDs)
- [ ] **AC-003**: Output format shows each AC with its mapped test(s) or "NO TEST FOUND"
- [ ] **AC-004**: Results are informational (soft gate) — warns but doesn't block

### LLM-Enhanced Mapping (P2 — better accuracy)
**Verify independently**: Run on feature where tests exist but don't follow naming conventions
- [ ] **AC-005**: LLM analysis maps test functions to ACs by semantic content (not just naming)
- [ ] **AC-006**: LLM mapping is optional — tool works without it (naming-only fallback)

### Integration
- [ ] **AC-007**: Coverage report available via `spec-analyze.sh` (R2 integration) or standalone tool
- [ ] **AC-008**: Works with both validate_framework.sh tests and project-specific test files

### Edge Cases
- [ ] **AC-009**: Features with no tests report 0/N coverage, not error
- [ ] **AC-010**: Features with no acceptance file produce clear error message
