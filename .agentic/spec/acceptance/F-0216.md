# F-0216: NFR Auto-Generation at Lifecycle Moments - Acceptance Criteria

**Feature**: Transform `ag nfr discover` into an active, recommendation-driven NFR generation flow with stack-based defaults and priority tiers.

---

## Behavior (what the user needs — technology-agnostic)

When starting a project or running `ag nfr discover`, the user gets smart NFR recommendations based on their technology stack (e.g., web app, API, CLI) — not the full catalog. They pick the ones that matter, customize thresholds, and NFR.md is populated automatically. During `ag kickoff`, NFR suggestions appear alongside generated features.

---

## Acceptance Criteria

### Generation Tool (P1 — MVP)
**Verify independently**: Run `nfr-generate.sh` with various `--project-type` values and verify output

- [x] **AC-001**: `nfr-generate.sh` reads `Primary platform:` from STACK.md and outputs applicable NFR suggestions
- [x] **AC-002**: `nfr-generate.sh --project-type web` returns web-specific NFRs from catalog
- [x] **AC-003**: `nfr-generate.sh` respects P1/P2/P3 tiers — P1 always included, P2 on component match, P3 omitted unless `--all`
- [x] **AC-004**: Output format is structured (one block per NFR: ID, category, statement, threshold, applies-to)

### Discovery Flow (P1 — MVP)
**Verify independently**: Run `ag nfr discover` and verify interactive flow

- [x] **AC-005**: `ag nfr discover` calls `nfr-generate.sh` and presents 4-8 pre-selected recommendations
- [x] **AC-006**: Selected NFRs are written to NFR.md with proper NFR-XXXX IDs (no collisions with existing)
- [x] **AC-007**: `ag nfr discover` merges with existing NFRs (doesn't overwrite)

### Kickoff Integration (P2 — better but optional)
**Verify independently**: Run `ag kickoff` and check staging output

- [x] **AC-008**: `cmd_kickoff` in ag.sh calls `nfr-generate.sh` during kickoff flow (at ag.sh layer, NOT inside kickoff.py)
- [x] **AC-009**: NFR suggestions appear in staging area alongside generated features

### Catalog Expansion (P1 — MVP)
**Verify independently**: Inspect nfr-catalog.md structure

- [x] **AC-010**: `nfr-catalog.md` has Library/SDK and Data Pipeline project types with appropriate NFRs
- [x] **AC-011**: All catalog entries have P1/P2/P3 priority tier column
- [x] **AC-012**: Platform detection in ag.sh maps `library`, `sdk`, `data-pipeline`, `pipeline` to new catalog sections

### Component-Level Scoping (P2 — better but optional)
**Verify independently**: Create NFR with component tag and verify matching

- [x] **AC-013**: NFR.md supports `Applies to: component:frontend, component:backend` syntax
- [x] **AC-014**: `nfr-applicable.sh` matches component tags against feature Category/description keywords

### NFR Constraints (P1 — required)

- [x] **AC-015**: Existing tests continue to pass after catalog expansion (NFR-0004)
- [x] **AC-016**: Max 10 files per commit, split into 2 commits if needed (NFR-0003)
