# F-0123: Intelligent Onboarding for Existing Projects - Acceptance Criteria

**Feature**: Auto-analyze existing codebases during `ag init` and generate populated specs
**Status**: planned

---

## Acceptance Criteria

### AC-1: Existing Codebase Detection

- [ ] `ag init` detects existing code (non-empty directory with source files)
- [ ] Offers choice: auto-discover mode vs full interactive interview
- [ ] Both paths converge to the same output (populated state files)
- [ ] Works for both Discovery and Formal profiles

### AC-2: Auto-Discover Mode

- [ ] Analyzes code structure (directories, file types, entry points)
- [ ] Reads README.md/README if present for project description
- [ ] Inspects existing tests to infer test patterns and coverage
- [ ] Detects tech stack (language, framework, build tools, package manager)
- [ ] Generates populated STACK.md with detected stack info
- [ ] Generates populated CONTEXT_PACK.md with architecture snapshot
- [ ] Generates populated OVERVIEW.md with project description

### AC-3: Feature Discovery (Formal)

- [ ] Identifies existing features from code structure, modules, routes, etc.
- [ ] Generates FEATURES.md with discovered features marked as `shipped`
- [ ] Creates acceptance criteria files for discovered features (best-effort)
- [ ] Feature IDs assigned sequentially starting from F-0001
- [ ] Feature descriptions derived from code analysis, not hallucinated

### AC-4: Interactive Mode

- [ ] Asks guided questions about project purpose, stack, architecture
- [ ] Uses answers to populate same output files as auto-discover
- [ ] Can be combined with auto-discover (auto-discover proposes, human confirms/edits)
- [ ] Graceful handling of "I don't know" answers (skip or use defaults)

### AC-5: Proposal Workflow (Human Approval Required)

- [ ] All generated specs are marked as proposals (not official)
- [ ] Clear visual indicator that specs need human review (e.g., `<!-- PROPOSAL -->` marker)
- [ ] Human must explicitly approve proposals before they become official
- [ ] `ag approve-onboarding` or similar command to batch-approve
- [ ] Unapproved proposals do not block normal framework operation

### AC-6: Quality Safeguards

- [ ] Never invents features not evidenced by code
- [ ] Clearly marks confidence level (high/medium/low) on discovered items
- [ ] Logs what was analyzed and what was inferred in a discovery report
- [ ] Handles empty/minimal codebases gracefully (falls back to standard init)

### AC-7: Integration with Existing Init Flow

- [ ] Does not break standard `ag init` for new/empty projects
- [ ] Reuses existing scaffold.sh and templates where possible
- [ ] Generated files follow existing template formats exactly
- [ ] install.sh still works as entry point (onboarding triggered after install)

---

## Out of Scope (v1)

- Test generation from discovered features (future enhancement)
- CI/CD configuration detection
- Dependency vulnerability scanning
- Automatic git history analysis for feature timeline
- Multi-language project support (v1: primary language only)

## Test Scenarios

1. **Empty project**: Standard init flow, no auto-discover offered
2. **Node.js project**: Detects package.json, README, test dir, generates stack
3. **Python project**: Detects requirements.txt/pyproject.toml, generates stack
4. **Monorepo**: Handles multiple modules, creates features per module
5. **No README**: Gracefully handles missing documentation
6. **User declines auto-discover**: Falls back to interactive mode
7. **Approval flow**: Generated proposals reviewable and approvable
