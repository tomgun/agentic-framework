## Context

**Problem**: NFRs in the framework are currently passive documentation. PR #141 (v0.61.0) built significant infrastructure — shared AC parser, NFR→AC inline integration, staleness detection, `nfr-applicable.sh` scope matching — but NFRs still don't *actively propagate* to features, tests, or health checks. Projects start with no NFRs (or have to manually read a catalog), and there's no lifecycle for discovering, refining, propagating, enforcing, and evolving them.

**Origin**: TODOs T-0025 (NFRs as live invariants) and T-0067 (NFR lifecycle auto-generation), both natural follow-ups to PR #141's quality infrastructure.

**Intended outcome**: Make NFRs the best part of the framework — smart defaults at project init, automatic propagation into feature ACs and tests, health dashboards at scale, and capture triggers that prevent quality constraints from staying informal.

**Bug fix included**: `nfr_validator.py` has `VALID_NFR_CATEGORIES` missing `process` (used by NFR-0003, NFR-0004), `realtime-safety`, `data`, `documentation`, `accessibility`, `quality` (all used in `nfr-catalog.md`). **Confirmed**: the dogfooding test (`test_framework_nfr_passes_validation`) is ALREADY FAILING due to this bug. Also: NFR-0004 references a glob path `tests/infrastructure/structural/S07_*` which the validator can't resolve — this must be fixed too.

**Prerequisite**: Before implementing any feature, create FEATURES.md entries and acceptance criteria stubs for F-0216 through F-0219. This is the framework's spec-first rule (NFR-0004).

## Cross-Cutting Design Decisions

### Dual-format NFR section support

Existing acceptance files (17 files — 15 features + NFR-0003.md + NFR-0004.md) use `## NFR Compliance` (legacy heading). New features use `### NFR Constraints` (inline, introduced in v0.61.0). `check-spec-health.sh` already handles both formats (lines 71-74). **All new tools** (`nfr-test-check.sh`, `nfr-propagate.sh sync`, `nfr-health.sh`) MUST recognize both `## NFR Compliance` and `### NFR Constraints` sections. Format migration is not forced — legacy files work as-is, new files use the new format.

### Machine-readable output from `nfr-applicable.sh`

`nfr-applicable.sh` already disables ANSI colors when stdout is not a TTY (lines 21-26: `if [ -t 1 ]; then ... else GREEN='' ... fi`). Tools that pipe its output (`nfr-propagate.sh derive`, `nfr-test-check.sh`) get clean text automatically. No `--raw` flag needed — the existing TTY detection is sufficient.

### `spec_writing.md` has THREE NFR instruction points

All three must be updated together in F-0218:
1. **Step 2** (line 29-34): "Active NFR matching — read NFR.md and evaluate EACH defined NFR" → replace with `nfr-propagate.sh derive`
2. **Step 4** (line 38): "Add `### NFR Compliance` section" → update to reference `### NFR Constraints` and note it's auto-generated by derive
3. **NFR Integration section** (lines 99-108): Steps 1-5 with manual matching → replace with tool-based workflow

### `check-spec-health.sh` dead code

Lines 159-169 reference `spec/tools/consistency.py` and `spec/tools/nfr_validator.py` — both wrong paths (should be `.agentic/lib/tools/`). These are dead code. F-0218 should fix these paths while integrating `nfr-propagate.sh check`.

### `ac_list_nfr_refs()` overmatch

`ac_list_nfr_refs()` in `ac-parse.sh` (line 233) does `grep -oE 'NFR-[0-9]+' "$file"` on the entire file — catching NFR references in comments, headings, and notes, not just ACs. For F-0217's `nfr-test-check.sh`, NFR reference extraction must be scoped: extract from within `## Acceptance Criteria` and `### NFR Constraints`/`## NFR Compliance` sections only, using `sed -n` section extraction before grepping. Do NOT rely on `ac_list_nfr_refs()` for coverage analysis.

### Instruction file coordination for parallel F-0216 / F-0217

Both features update `memory-seed.md`. To avoid merge conflicts: F-0216 updates the NFR discover trigger section, F-0217 updates the test-writing trigger section. These are in different parts of the file. Both PRs bump the version marker — this is a guaranteed trivial merge conflict (just take the higher version). If other conflicts arise, they're similarly resolvable (both additions are independent).

### P1/P2/P3 priority tier assignment criteria

When adding priority tiers to `nfr-catalog.md` entries:
- **P1** (always include): NFRs that apply universally within the project type and would be embarrassing to miss. Examples: LCP for web apps, p95 latency for APIs, startup time for CLIs, no heap allocs on audio thread for DSP. Rule of thumb: if a customer would notice this failing on day 1, it's P1.
- **P2** (include on component/context match): NFRs that matter but only for specific components or when specific conditions hold. Examples: bundle size (only if SPA), CSRF protection (only if state-changing endpoints), offline support (only if mobile app claims offline capability). Rule of thumb: important but conditional.
- **P3** (structural/CI-only, omitted from discover): Process-level or structural NFRs that are enforced by tooling, not by feature-level ACs. Examples: max files per commit, spec-first rule. Rule of thumb: the framework already enforces this, agents don't need to write ACs for it.

Each existing catalog entry gets a tier during F-0216 implementation. Universal entries (U-01 through U-04) are P1. Framework Promises (F-01 through F-04) are P3. Other sections: typically 2-3 P1, 2-3 P2, 0-1 P3 per project type.

### Component-to-feature mapping (no new FEATURES.md field)

FEATURES.md has no `Component:` field — only Status, Category, Priority, Complexity, Since, Dependencies. Adding a new field would require changes to all existing entries and tooling. Instead, component matching uses the existing `Category` field plus keyword matching against the feature description (same approach `nfr-applicable.sh` already uses for scope matching). NFR entries with `Applies to: component:frontend` match features whose Category or description contains "frontend", "UI", "client", etc. This is fuzzy but consistent with the existing matching approach. If projects need precise component mapping in the future, a `Components:` field can be added to FEATURES.md — but that's a separate feature, not part of this epic.

### Relationship to existing `nfr-migrate.sh`

`nfr-migrate.sh` (exists at `.agentic/lib/tools/nfr-migrate.sh`) migrates `## NFR Compliance` sections into inline `### NFR Constraints` format, creating AC-010+ entries and optionally generating migration records for shipped features. **Relationship to `nfr-propagate.sh sync` (F-0218)**: `sync` COMPARES current state vs desired state and reports gaps — it's a read-only diagnostic. `nfr-migrate.sh` WRITES the conversion — it's the action tool. They complement each other: `sync` detects "this feature has legacy format or missing NFR constraints", `nfr-migrate.sh` fixes it. F-0218 should update `nfr-propagate.sh sync` to suggest running `nfr-migrate.sh` when it detects legacy-format sections.

### Acceptance template coordination (F-0218)

The acceptance template (`.agentic/lib/templates/acceptance.template.md`) already has the new `### NFR Constraints (P1 — required)` section with AC-010+ numbering AND a deprecated `## NFR Compliance` section that directs to `nfr-migrate.sh`. Since `nfr-propagate.sh derive` auto-generates the `### NFR Constraints` section, F-0218 should update the template to note: "This section is auto-populated by `nfr-propagate.sh derive F-XXXX` — review and customize." The deprecated `## NFR Compliance` section stays as-is (it already points to migration).

## F-0216: NFR Auto-Generation at Lifecycle Moments

**What**: Transform `ag nfr discover` from a passive catalog pointer into an active, recommendation-driven generation flow. Integrate into `ag kickoff` (at the ag.sh/skill layer, not inside kickoff.py). Fix the validator category bug.

**Why independently valuable**: Every new project immediately gets smart NFR defaults instead of starting empty. Existing projects can re-run `ag nfr discover` to pick up new catalog entries after framework upgrades.

### Key Changes

1. **New `nfr-generate.sh`** (~180 lines) — Reads STACK.md `Primary platform:` to determine project type, loads `nfr-catalog.md`, outputs structured list of applicable NFR suggestions. Accepts `--project-type <type>` override and `--components <list>` for component-scoped suggestions. Output: one NFR per block with ID, category, statement, threshold, applies-to.

2. **Enhance `cmd_nfr` in `ag.sh`** — `ag nfr discover` calls `nfr-generate.sh`, presents pre-selected recommendations (5-8, not full catalog), waits for agent/user refinement, writes to NFR.md with proper NFR-XXXX IDs. Handles merge with existing NFRs (no ID collisions).

   **Selection heuristic**: Stack detection (`Primary platform:` from STACK.md) selects the project type. Within that type, all P1 entries are always included. P2 entries are included when their component tags match project components (if specified). P3 entries are omitted from discover but available via `--all`. Typical result: 4-6 NFRs for a simple project, up to 8 for multi-component.

3. **Integrate into kickoff flow at the `ag.sh`/skill layer** — The `cmd_kickoff` function in `ag.sh` calls `nfr-generate.sh` after feature generation but before promotion. NFR suggestions are written to the staging area alongside features. **Note**: `kickoff.py` is agent-agnostic and accepts structured data only — it does NOT call external tools. The NFR integration goes in the ag.sh orchestration layer that calls kickoff.py, not inside kickoff.py itself.

4. **Validator bugfix (extracted to Order 0.5)** — The `VALID_NFR_CATEGORIES` expansion and NFR-0004 glob path fix ship as a preliminary bugfix PR to unblock the already-failing dogfooding test immediately. This reduces F-0216's file count from 10 to 8 in the first commit, giving headroom. F-0216 depends on this bugfix being merged first.

5. **Expand `nfr-catalog.md`** (~100 lines changed) — Add missing project types: Library/SDK (backward compat, API surface, dependency bloat), Data Pipeline (zero data loss, idempotent reruns, observability). Add priority tiers (P1/P2/P3) as a new column in each project-type table — this touches all 9 existing tables (40+ entries) plus 2 new tables. Also add `Primary platform:` detection values for the new types.

6. **Add platform detection mapping** — Update the `ag.sh` cmd_nfr platform detection chain (line ~3749) to map `library`, `sdk`, `data-pipeline`, `pipeline` to the new catalog sections. Without this, the new catalog entries would be unreachable via auto-detection.

7. **Component-level support** — Extend NFR.md format to support `Applies to: component:frontend, component:backend`. Update `nfr-applicable.sh` to match component tags against feature metadata.

## F-0217: NFR-Aware Test Writing

**What**: Make the writing-tests workflow check applicable NFRs before designing test plans. Catch the gap where features pass their own ACs but violate NFRs.

**Why independently valuable**: Agents start ensuring test plans cover NFR constraints immediately, without waiting for the propagation pipeline.

### Key Changes

1. **New `nfr-test-check.sh`** (~120 lines) — Given a feature ID, outputs: applicable NFRs, which have test references in the AC file, which are missing. Exit code: 0 = all covered, 1 = gaps found. Uses `nfr-applicable.sh` for applicability matching (piped output is clean — `nfr-applicable.sh` auto-disables ANSI colors when stdout is not a TTY).

Does NOT use `ac_list_nfr_refs()` which greps the entire file and would over-report coverage. Both legacy (`## NFR Compliance`) and new (`### NFR Constraints`) section formats are recognized.

3. **Update implementing-features skill** — Step 4 (Implement): note to check applicable NFRs with `nfr-test-check.sh` when writing tests.

4. **Enhance `spec-audit.sh`** — Add `--nfr-test-coverage` flag: for all shipped features with NFR references, check if tests cover the NFR constraints. Summary output.

## F-0218: NFR Propagation Pipeline

**What**: Make NFR.md the living source of truth that actively propagates. Auto-derive NFR Constraints sections, detect staleness across all features, capture informal invariants.

**Why independently valuable**: NFR-to-feature mapping becomes automated instead of manual. When NFR.md changes, affected features are flagged. The "it must always..." capture trigger becomes a real tool.

### Key Changes

1. **New `nfr-propagate.sh`** (~220 lines) — Three modes:
   - `derive F-XXXX`: Outputs a draft `### NFR Constraints` section for the feature (using `nfr-applicable.sh` — piped output is clean, no ANSI codes), ready for insertion into an acceptance file. **How derive works**: calls `nfr-applicable.sh F-XXXX` to get applicable NFRs, then for each match reads the NFR entry from NFR.md to extract the statement and threshold, and templates them into a `### NFR Constraints` markdown section with one AC per applicable NFR.
   - `check [--all]`: For each feature with NFR references, check if NFR.md changed since AC was written (extends staleness from `ag.sh` to standalone tool)
   - `sync F-XXXX`: Compare current NFR constraints in AC vs what `derive` would produce; flag missing/outdated/extra. **Recognizes both** `## NFR Compliance` (legacy) and `### NFR Constraints` (new) section formats.

2. **New `nfr-capture.sh`** (~100 lines) — Validates an invariant statement, assigns next NFR-XXXX ID, writes to NFR.md, optionally runs `nfr-propagate.sh check` to flag affected features. Called by agents when they detect constraint language. **Concurrency safety**: reads NFR.md, finds max NFR-XXXX ID, increments. For multi-agent safety, uses the framework's existing collision guard: `agents_helpers.py count-others` check before writing. If another agent is active, logs to TODO.md instead and flags for human resolution.

3. **Enhance `check-spec-health.sh`** — Integrate `nfr-propagate.sh check` into the health flow. NFR staleness becomes part of spec health, not just an `ag implement` advisory. **Exit code handling**: `set -euo pipefail` means `|| true` pattern with exit code stored separately. **Also fix dead code**: update lines 159-169 to reference `.agentic/lib/tools/nfr_validator.py` instead of `spec/tools/nfr_validator.py` (and same for consistency.py).

4. **Update `spec_writing.md`** — ALL THREE NFR instruction points updated together:
   - **Step 2** (lines 29-34): Replace manual "evaluate EACH defined NFR" with: "Run `nfr-propagate.sh derive F-XXXX` to get draft NFR Constraints section. Review output for applicability, then insert into the acceptance file."
   - **Step 4** (line 38): Update `### NFR Compliance` to `### NFR Constraints` and note: "auto-generated by `nfr-propagate.sh derive` — review and insert"
   - **NFR Integration section** (lines 99-108): Replace manual 5-step workflow with tool-based workflow: (1) Run `nfr-propagate.sh derive F-XXXX`, (2) Review and insert, (3) Add `NFRs:` field to FEATURES.md, (4) Promotion check remains manual

5. **Enhance `ag implement`** — After existing staleness warning, add: "Run `nfr-propagate.sh sync F-XXXX`" when staleness detected. Advisory, not blocking.

## F-0219: NFR Health Dashboard & Scale

**What**: Comprehensive NFR health view, dashboard integration, scale handling for 20+ NFRs. The observability layer that ties everything together.

**Why independently valuable**: Projects with many NFRs can see at a glance which are healthy, drifting, or untested. Makes NFRs feel managed, not overwhelming.

### Relationship to `nfr-coverage.sh`

The existing `nfr-coverage.sh` (131 lines) tracks which features reference each NFR and whether acceptance files have NFR Compliance sections. `nfr-health.sh` is a **superset** that adds: status aggregation (met/partial/violated), staleness detection, test coverage analysis, and machine-readable output. **Decision**: `nfr-health.sh` wraps `nfr-coverage.sh`'s logic internally (reuses the reference-counting approach) and `ag nfr coverage` becomes an alias for `ag nfr health --coverage-only`. The old `nfr-coverage.sh` is kept for backward compatibility but `cmd_nfr` routes to `nfr-health.sh`. **Output format note**: `--coverage-only` mode preserves the same human-readable format as `nfr-coverage.sh` (NFR ID, name, feature count, per-feature status) to avoid breaking scripts or user expectations.

### Key Changes

1. **New `nfr-health.sh`** (~180 lines) — Per-NFR report: status (met/partial/violated), coverage (how many features reference it), staleness (features needing sync), test coverage. Summary + detail modes. `--json` for machine consumption. `--component <name>` for filtering. `--coverage-only` mode for backward-compatible coverage report. **Recognizes both** `## NFR Compliance` and `### NFR Constraints` section formats.

2. **Dashboard integration** — `dashboard.sh` shows NFR health line when NFR.md exists: `"NFRs: 4 defined, 3 met, 1 partial"`. Uses `nfr-health.sh --summary`. **Performance**: `--summary` mode only parses NFR.md status fields (no cross-referencing features), keeping latency under 100ms. Full health analysis runs only on explicit `ag nfr health`.

3. **Retrospective integration** — Update `retrospective.md` NFR Health section to reference `nfr-health.sh` with specific recommendations.

4. **Scale: applicability caching** — `nfr-applicable.sh` gets optional cache at `.agentic/session/.nfr-cache.json`. Invalidated when NFR.md or FEATURES.md git timestamps change. Relevant for projects with 10+ NFRs. **Extension point note**: F-0216's component matching additions to `nfr-applicable.sh` are structured so the caching layer wraps the entire check (cache key = NFR.md mtime + FEATURES.md mtime + feature ID; cache value = list of applicable NFR IDs).

5. **`ag nfr` subcommand hub** (~45 lines) — `ag nfr health`, `ag nfr sync F-XXXX`, `ag nfr test-check F-XXXX`, `ag nfr capture "statement"`. Central entry point for all NFR operations. Current `cmd_nfr` is 32 lines handling 4 subcommands; adding 4 more with proper help text requires ~45 lines net.

6. **Priority-based filtering** — `nfr-applicable.sh --p1-only` for AC inclusion (only critical NFRs), `--all` for audits. Prevents AC bloat with 20+ NFRs.

## What Makes This Shine

1. **NFRs prevent bugs before they happen** — `nfr-propagate.sh derive` auto-generates the NFR Constraints section. Agents don't manually read NFR.md and guess what applies — the tool tells them.

2. **Discovery is delightful, not bureaucratic** — `ag nfr discover` presents 5-8 pre-selected recommendations based on stack detection + priority tiers. "looks good" is a valid answer. 60 seconds, not 5 minutes.

3. **Complete lifecycle**: discover (F-0216) → refine (F-0216) → propagate (F-0218) → test (F-0217) → monitor (F-0219) → evolve (F-0218 capture)

4. **20+ NFRs feel managed** — Priority tiers (P1/P2/P3) prevent AC bloat. Component scoping shows relevant NFRs per area. Health dashboard gives one-glance status.

5. **Informal invariants get captured** — `nfr-capture.sh` turns "it must always..." into structured NFRs. No more quality constraints living only in chat history.

6. **NFRs feel like lint rules for requirements** — invisible when met automatically, visible when violated. Not compliance paperwork.

## Known Acceptable Weaknesses

These were identified in review and are explicitly accepted:

1. **NFR conflict detection** — Not addressed. If NFR-0001 says "files under 100 lines" and NFR-0005 says "comprehensive inline docs," they may conflict. Conflict detection requires semantic understanding; this epic focuses on lifecycle mechanics. Can be a future feature.

2. **Capture trigger is probabilistic** — `nfr-capture.sh` depends on agents recognizing constraint language ("it must always..."). Memory-seed triggers improve probability but can't guarantee capture. This is inherent to behavioral triggers in the framework.

3. **TOCTOU gap in NFR ID assignment** — `agents_helpers.py count-others` check has a race window between check and write. For the rare multi-agent + simultaneous NFR capture case, the TODO.md fallback is pragmatic. A file lock would be over-engineering for current usage patterns.

4. **Bash complexity** — 5 new shell scripts (180 + 120 + 220 + 100 + 180 = 800 lines total). Consistent with framework patterns but harder to test than Python. Mitigated by fixture-based tests and three-layer verification.

5. **Component matching is fuzzy** — Feature-to-component mapping uses keyword matching against FEATURES.md Category + description (no dedicated `Components:` field exists). NFR entries with `Applies to: component:frontend` match via string overlap, not structured metadata. False positives/negatives are possible. Acceptable because: (a) consistent with existing `nfr-applicable.sh` approach, (b) `--project-type` override provides an escape hatch, (c) adding a `Components:` field to FEATURES.md is a separate future enhancement.

6. **Dashboard `--summary` 100ms target is unverified** — Claimed but not benchmarked. The design (parse NFR.md `Current status:` fields only, no cross-referencing) is sound for typical projects (4-8 NFRs). For 20+ NFRs, bash startup + file parsing may approach the budget. Acceptable because: (a) conditional on NFR.md existing, (b) can be benchmarked and optimized during implementation, (c) `nfr-health.sh` can cache the summary output in `.agentic/session/` if needed.

7. **`nfr-coverage.sh` output format may drift** — `ag nfr coverage` becomes alias for `nfr-health.sh --coverage-only`, which aims to preserve the same output format. But format parity is best-effort, not guaranteed. Scripts parsing `nfr-coverage.sh` output directly (not via `ag nfr coverage`) continue working since the file is kept. Acceptable because: (a) `nfr-coverage.sh` is kept for backward compat, (b) the alias path explicitly targets format preservation, (c) no known external consumers.

8. **Applicability cache invalidation is conservative** — F-0219's cache key (NFR.md mtime + FEATURES.md mtime + feature ID) invalidates on ANY edit to NFR.md, including comments. For projects with frequent NFR.md edits and 20+ NFRs, this means frequent cache misses. Acceptable because: (a) false invalidation is safe (never stale), (b) 20+ NFRs with frequent edits is a rare edge case, (c) without caching the tool still works correctly, just slower.
