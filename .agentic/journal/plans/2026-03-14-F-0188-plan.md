# F-0188: End-to-End Autonomous Flow — Implementation Plan (REVISED)

**Status**: APPROVED
**Revision**: 3 — incorporates rounds 1+2 dialectical review findings

## Context

F-0188 is the ADR-001 Phase 7 capstone: wiring all existing autonomous modules into a single pipeline that takes a user's vision and produces shipped features — fully autonomously. All component modules are shipped and individually tested. The gap is **orchestration glue**: no single function chains kickoff → promote → epic-create → schedule → ship.

---

## Review Findings Incorporated

1. **Gate bypass (R-2)**: Pipeline refuses to start if `review_decomposition: human` — prints guidance to use `critical_agent` or `skip`.
2. **No retroactive Parent injection (R-4/C-1)**: Instead of retroactively patching FEATURES.md after promotion, we create the epic FIRST, then promote with `parent_id` so children are born with their Parent link. Zero fragile regex injection.
3. **ID allocation (R-1)**: Epic ID allocated first, child IDs allocated sequentially in promote. Single process, sequential calls — documented as non-concurrent.
4. **AC-002 boundary (G-1)**: `features_data` is pre-structured input. The LLM vision→features step is the caller's responsibility (ag.sh/skill layer). Documented in docstring and CLI help.

---

## Approach

### Pipeline phases (revised sequencing):

1. **gate_check** — Validate `review_decomposition` is not `human`. Fail fast with guidance.
2. **epic_create** — Allocate epic ID via `get_next_feature_id()`, append epic section to FEATURES.md, create synthetic AC file. Returns `epic_id`.
3. **kickoff** — `generate_to_staging(project_root, features_data, overview_text)`. Writes staged features.
4. **promote** — `promote_staging_with_ids(project_root, force_overview, parent_id=epic_id)`. Promotes staged features to FEATURES.md with `**Parent**: {epic_id}` included at write time. Returns `id_map`.
5. **schedule** — `AutonomousScheduler(project_root).run_epic(epic_id)`. Inherits AC-003 (integration verify), AC-004 (review checkpoints), AC-005 (escalation).

Key change from v1: epic is created BEFORE children are promoted, so `**Parent**` is written at promotion time — no retroactive file editing.

### AC-002: User Input Boundary

`run_pipeline()` accepts `features_data: list[dict]` — the same structured format as `generate_to_staging()`. The LLM call that converts a user's vision/prompt/research into `features_data` happens at the ag.sh/skill layer, not in pipeline.py. This keeps the Python layer fully testable and agent-agnostic (consistent with kickoff.py's design — see its docstring line 8).

### AC-003/004/005: Already wired

Inherited by calling `AutonomousScheduler.run_epic()`. No new code needed.

## Detailed Design

### `promote_staging_with_ids()` (kickoff.py)

Refactor `promote_staging()` into `_promote_staging_impl()`:

```python
def _promote_staging_impl(
    project_root: Path,
    force_overview: bool = False,
    parent_id: str = "",
) -> tuple[bool, list[str], dict[str, str]]:
    """Core promote logic returning (success, messages, id_map).

    When parent_id is set, each promoted feature gets **Parent**: {parent_id}
    in its FEATURES.md section (written at creation time, not retroactively).
    """
```

- `promote_staging()` — existing public API, unchanged signature. Wrapper calling `_promote_staging_impl()`, drops id_map. Existing callers (`ag kickoff --approve`) unaffected.
- `promote_staging_with_ids()` — NEW public API. Returns `(success, messages, id_map)`, accepts `parent_id`. Only called by pipeline.
- The `parent_id` field is injected into the section_lines list at line ~873, right after `**Category**`

### `_create_epic_entry()` (pipeline.py)

Simple helper (NOT using `create_child_features` which creates children — here we only create the epic itself):

1. Calls `get_next_feature_id(features_file)` to allocate an ID
2. Appends an epic section to FEATURES.md:
   ```
   ## F-XXXX: {epic_name}
   **Status**: planned
   **Category**: Epic
   ```
3. Creates a synthetic AC file referencing "children will be added by pipeline"
4. Returns `(epic_id, messages)`

No child manipulation. Children are linked during promote via `parent_id`.

### `run_pipeline()` (pipeline.py)

```python
@dataclass
class PipelineResult:
    success: bool
    phase: str = ""           # gate_check | epic_create | kickoff | promote | schedule | done
    epic_id: str = ""
    feature_ids: list[str] = field(default_factory=list)
    scheduler_result: SchedulerResult | None = None
    blocked_reason: str = ""
    messages: list[str] = field(default_factory=list)

def run_pipeline(
    project_root: Path,
    features_data: list[dict],       # Same format as kickoff.generate_to_staging
    overview_text: str = "",
    epic_name: str = "Pipeline Epic",
    force_overview: bool = False,
    max_errors: int = 3,
    skip_pr: bool = False,
    claude_command: str = "claude",
) -> PipelineResult:
```

Gate check at the top:
```python
review_mode = get_setting(project_root, "review_decomposition", "skip")
if review_mode == "human":
    return PipelineResult(
        success=False, phase="gate_check",
        blocked_reason="review_decomposition is set to 'human'. "
        "Pipeline requires 'critical_agent' or 'skip'. "
        "Set in STACK.md ## Settings."
    )
```

## Failure Contract

On partial failure, the pipeline may leave artifacts in an intermediate state:

- **Failure at gate_check**: No side effects. Safe to re-run.
- **Failure at epic_create**: Epic entry may exist in FEATURES.md with no children. Recovery: delete the orphaned `## F-XXXX` section, or proceed to `ag auto epic F-XXXX` after manually adding children.
- **Failure at kickoff**: Epic exists, staging may be partial. Recovery: `ag kickoff --discard` then re-run pipeline.
- **Failure at promote**: Epic exists, staging may be partially promoted. Recovery: manual cleanup of FEATURES.md, then `ag kickoff --discard`.
- **Failure at schedule**: Epic + children exist. Recovery: `ag auto epic {epic_id}` resumes scheduling directly.

The pipeline is NOT idempotent — re-running after partial success will create duplicate epics. This is documented in CLI help.

## Limitations (documented, not fixed in v1)

- **Non-concurrent**: `get_next_feature_id()` is not atomic. Two simultaneous pipelines could collide on IDs. Acceptable because pipelines are heavyweight (minutes to hours) and unlikely to overlap.
- **No resume**: If pipeline fails mid-run, see Failure Contract above for per-phase recovery.
- **AC-002 boundary**: `features_data` must be pre-structured. The vision-to-features LLM call is the caller's responsibility.
