# Implementation Plan: F-0152 & F-0153 (Semantic Consistency Analysis + AC-Level Coverage)

## Context

F-0148 through F-0151 (SDD Toolkit Insights batch 1) are implemented. The user asked to also implement the two deferred recommendations: R2 (Semantic Consistency Analysis → F-0152) and R7 (AC-Level Coverage Tracking → F-0153). Acceptance criteria already written at `spec/acceptance/F-0152.md` and `spec/acceptance/F-0153.md`.

**Problem**: Our spec tooling validates **structure** (files exist, sections present, cross-references valid) but not **semantics** (vague requirements, missing test coverage per AC, unmeasurable NFRs). Agents can implement features with undetected spec gaps.

**Goal**: Deterministic P1 checks that catch the most common spec problems before implementation starts, plus AC-level test coverage reporting. Advisory only (warn, don't block).

## Phase 1: F-0152 — Semantic Consistency Analysis (P1 only)

### New file: `.agentic/tools/spec-analyze.sh`

Bash script — the main orchestrator. Interface:

```
bash .agentic/tools/spec-analyze.sh F-XXXX        # Analyze one feature
bash .agentic/tools/spec-analyze.sh --help         # Usage info
```

**Structure** (follows `check-spec-health.sh` pattern):
1. Parse feature ID argument
2. Locate acceptance file at `spec/acceptance/F-XXXX.md`
3. Run 3 deterministic checks (no LLM calls):
   - **Check 1: Ambiguity detection** — scan AC text for vague words without metrics
   - **Check 2: AC↔test coverage gaps** — call `coverage.py --ac-coverage F-XXXX`
   - **Check 3: NFR measurability** — scan NFR.md entries for vague measurement criteria
4. Output severity-rated findings
5. Exit 0 always (advisory) — print summary with warning/finding counts

**Check 1 — Ambiguity detection** (in spec-analyze.sh):
- Word list: `fast|slow|scalable|easy|simple|intuitive|secure|robust|efficient|flexible|responsive|user-friendly|seamless|modern|clean|good|nice|better|improved|optimal`
- Scan: grep AC lines in acceptance file for these words
- Severity: MEDIUM per match (adjective without a metric)
- Skip lines that contain numbers or measurement units nearby (within 5 words)

**Check 2 — AC↔test coverage** (delegates to `coverage.py --ac-coverage`):
- See Phase 2 (F-0153) below — this check calls the coverage tool

**Check 3 — NFR measurability** (in spec-analyze.sh):
- Parse `spec/NFR.md` for "How to measure" fields
- Flag entries where the measurement is a placeholder or uses vague words without numbers/units
- Also cross-check: does the acceptance file reference any NFRs? If the feature's NFR Compliance section lists NFR-XXXX, verify that NFR exists
- Severity: HIGH for placeholder measurements, MEDIUM for vague measurements

**Output format**:
```
=== Spec Analysis: F-0152 ===

[MEDIUM] AC-003: Contains vague term "fast" without metric
  → Consider: "responds within 200ms" instead of "fast"
[HIGH] NFR-0005: "How to measure" is a placeholder
[MEDIUM] AC-007: No test found for this acceptance criterion

Summary: 0 CRITICAL, 1 HIGH, 2 MEDIUM, 0 LOW
```

## Phase 2: F-0153 — AC-Level Coverage Tracking (P1 only)

### Modified: `.agentic/tools/coverage.py`

Add `--ac-coverage F-XXXX` mode. New function:

```python
def ac_level_coverage(root: Path, feature_id: str) -> dict:
    """Map individual ACs to tests using naming conventions.

    Strategy (deterministic, no LLM):
    1. Parse acceptance file for AC IDs (regex: r'\\*\\*AC-(\d+)\\*\\*')
    2. Find test files that reference this feature (existing test_mapping logic)
    3. Within those test files, search for AC ID references:
       - In test function names: test_ac_001, test_AC001, testAC_001
       - In comments: # AC-001, @ac AC-001
       - In assert messages containing AC-001
    4. Report: {ac_id: [matched_tests] or "NO TEST FOUND"}
    """
```

**Reuse from existing code**:
- `parse_features()` — already exists, reuse
- `TEST_FEATURE_RE` pattern — extend with AC-level: `AC[-_]?(\d{3})`
- `scan_test_feature_mapping()` — use Method 1 (naming) to find feature test files first

**Output** (human-readable):
```
=== AC Coverage: F-0042 ===

Feature: 6 ACs, 4 with tests (67%)
  ✅ AC-001: tests/validate_framework.sh (line 2650: "F-0042.*AC-001")
  ✅ AC-002: tests/validate_framework.sh (line 2655: "F-0042.*AC-002")
  ❌ AC-003: NO TEST FOUND — "rate limiting on rapid captures"
  ❌ AC-004: NO TEST FOUND — "duplicate detection"
  ✅ AC-005: tests/validate_framework.sh (line 2660)
  ✅ AC-006: tests/validate_framework.sh (line 2665)
```

**Output** (JSON, with `--json`):
```json
{
  "feature": "F-0042",
  "total_acs": 6,
  "covered": 4,
  "coverage_pct": 67,
  "acs": [
    {"id": "AC-001", "status": "covered", "tests": ["tests/validate_framework.sh:2650"]},
    {"id": "AC-003", "status": "not_covered", "text": "rate limiting on rapid captures"}
  ]
}
```

**How it finds tests** (naming convention strategy):
1. Search `tests/` directory for files containing the feature ID (e.g., `F-0042`, `F_0042`, `F0042`)
2. In `validate_framework.sh`: grep for lines containing both feature ID and AC ID
3. In Python/JS test files: search function names for AC ID patterns
4. In all test files: search comments for AC ID references

### Integration with spec-analyze.sh

`spec-analyze.sh` Check 2 calls:
```bash
python3 .agentic/tools/coverage.py --ac-coverage "$FEATURE_ID" --json 2>/dev/null
```
Parses JSON output, reports uncovered ACs as MEDIUM severity.
