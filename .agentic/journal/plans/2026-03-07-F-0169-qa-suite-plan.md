# Quality Assurance Suite — Implementation Plan

## Context

LLMs produce code and tests that *look* correct and pass CI, but may be subtly wrong — tests that assert nothing meaningful, acceptance criteria with vague language, NFRs that were never discussed. The framework promises "green coding" and "high quality" but these promises aren't enforced as formal constraints. Meanwhile, the retrospective system exists (340-line checklist, 467-line workflow, trigger scripts) but is **disabled by default** — no test project has ever seen the agent suggest one.

### The Three Quality Problems

These are fundamentally different concerns with different triggers and tooling:

| # | Problem | Question | When |
|---|---------|----------|------|
| **1. Creation** | Specs → criteria → tests → code produced correctly the first time | "Did we build the right chain?" | Feature specing & implementation |
| **2. Verification** | The chain *actually matches brilliantly* — not just "file exists" but "test validates what AC promises" | "Who tests the tests?" | Periodic audit, retrospective |
| **3. Propagation** | After specs/NFRs change, everything downstream is still in sync | "Is the chain still intact?" | After migrations, NFR changes |

**Problem 1** is mostly solved (spec-writing workflow, acceptance-driven development). Needs NFR integration.
**Problem 2** doesn't exist yet. The framework checks *structure* (file exists, section present) but not *substance* (does the test actually prove the AC?).
**Problem 3** doesn't exist yet. Migrations track *what changed* but nothing traces the ripple effect downstream.

This initiative addresses all three:
1. **Proactive Quality Assurance** — NFRs as a living concern, strengthening Problem 1
2. **Spec Verification Audit** — "Who tests the tests?" — solving Problem 2 with LLM-assisted review
3. **Change Propagation Pipeline** — solving Problem 3 with dependency tracing and remediation plans
4. **Retrospective Enforcement** — the recurring trigger that runs Problems 2 & 3 systematically

### Profile Applicability

| Capability | Discovery | Formal |
|-----------|-----------|--------|
| NFR catalog & discovery | Yes (lightweight guidelines) | Yes (formal, linked to criteria) |
| NFR enforcement in spec-writing | N/A (no specs) | Yes |
| Spec verification audit | N/A (no spec chain) | Yes |
| Change propagation tracking | N/A | Yes |
| Retrospective enforcement | Yes (journal-based retro) | Yes (full retro + spec audit) |
| QA tracker state machine | N/A | Yes |

**Discovery projects** don't have formal specs — only journal, plans, and git history. There's no chain to audit. But NFR.md can still serve as a **quality compass**: agents read it and follow constraints as guidelines during development, without formal acceptance criteria linking. When the project transitions Discovery → Formal, NFRs already captured become the seed for formal specs.

## Phase 1: NFR Discovery & Catalog (F-XXXX)

**Goal**: NFRs become a living, first-class concern — discussed at setup, revisited during development, and reviewed at retrospectives.

### New files
- **`.agentic/lib/init/nfr-catalog.md`** (~150 lines) — NFR suggestions by project type:
  - Universal (test coverage, maintainability)
  - Web App (LCP, bundle size, accessibility, XSS/CSRF)

  - Audio/DSP (realtime safety, CPU budget, latency, no glitches)
  - CLI (startup time, exit codes, signal handling)
  - Desktop (startup, memory, UI responsiveness)
  - Framework Promises (green coding, small batches, spec-first — suggested for all)
  - Each entry has pre-filled NFR fields (Category, Statement, How to measure, Where enforced) with customizable thresholds

### Modified files
- **`.agentic/lib/init/init_playbook.md`** — Add **Step 2c: NFR Discovery** after development style questions
  - Uses STACK.md platform/stack answers to select relevant catalog section
  - Presents type-specific suggestions, developer picks and customizes thresholds
  - Writes selected NFRs to `.agentic/spec/NFR.md`
  - **Formal**: required — NFRs link to acceptance criteria and are formally tracked
  - **Discovery**: optional but recommended — NFRs serve as **quality guidelines** agents follow without formal spec linking. Captured early so they're ready when/if transitioning to Formal.
  - Formalizes any constraints already mentioned in Step 2 question 4
- **`.agentic/lib/init/memory-seed.md`** — Add proactive suggestion: if NFR.md is template-only after 3+ shipped features, suggest NFR Discovery at session start

### Key design decisions
- Catalog is markdown, not code — agents read it and present relevant sections
- Developer picks and customizes, nothing is auto-applied
- Connects to existing Step 2 question 4 ("Key constraints?") which already captures informal constraints
- **NFRs are living documents** — not just a setup-time artifact (see NFR Lifecycle below)

### NFR Lifecycle (continuous, not one-time)

NFRs evolve throughout the project. Three mechanisms ensure they stay current:

1. **Reactive capture** (already exists in memory-seed): when user says "it must always..." or "never do X", create/update NFR
2. **Promotion detection** (new, Phase 2): during spec-writing, if the agent notices the same constraint appearing in 3+ feature acceptance files but NOT in project-wide NFR.md, it suggests promotion:
   > "I notice 'response time < 200ms' appears in F-0042, F-0055, and F-0067's acceptance criteria. Should this be a project-wide NFR?"
3. **NFR review during retrospective** (new, Phase 4): retro checklist includes:
   - Are any feature-scoped constraints ready for promotion to project NFR?
   - Are existing NFR thresholds still appropriate? (project grew, requirements changed)
   - Have new quality concerns emerged from bugs/incidents that should be NFRs?
   - `ag nfr discover` can be re-run anytime to review catalog suggestions against current project state

## Phase 3A: Spec Verification Tool (F-XXXX) — Formal Only

**Goal**: Solve Problem 2 — "Who tests the tests?" Does the test actually prove what the AC claims?

> Discovery projects don't have the spec chain. Phases 3A/3B/3C apply only to Formal profile. For existing projects: first audit is a one-time full review — no shortcuts.

### Verification — "Who Tests the Tests?"

This is NOT "does a test file exist?" (already solved by `check-spec-health.sh`). This is "does the test **actually prove** what the AC claims?"

**Example of the problem**: AC says "returns paginated results with cursor-based navigation". Test asserts `response.status_code == 200`. Test passes. AC is "covered." But the test proves nothing about pagination.

**Verification layers** (shallow → deep):

| Layer | Tool | What it catches | Cost |
|-------|------|-----------------|------|
| **Structural** | `check-spec-health.sh` | Missing files, missing sections | Fast, exists |
| **Coverage** | `coverage.py --ac-coverage` | ACs without any test reference | Fast, exists |
| **Semantic** | `spec-analyze.sh` | Vague ACs ("fast", "good UX") that can't be tested meaningfully | Fast, exists |
| **Test heuristics** | New: structural analysis | Empty test bodies, zero assertions, no negative cases | Fast, new |
| **Intent match** | New: **LLM review** | Test doesn't actually validate what AC promises | Token-expensive, new |

The LLM review is the breakthrough layer — it catches the "looks good but proves nothing" problem the user identified with AI-generated tests.

**LLM test review design**:
- **`.agentic/lib/tools/test-review-prompt.md`** (~50 lines) — Prompt template:
  - Input: AC text + test source code (scoped, token-efficient)
  - Questions the LLM answers:
    1. Does this test exercise the specific behavior described in the AC?
    2. Are assertions checking the right thing? (not just status codes)
    3. Could this test pass with a broken implementation? (the key question)
    4. Does the test cover edge cases mentioned or implied by the AC?
    5. Is this a real test or a "looks like a test" placeholder?
  - Output: `pass` / `concern` / `fail` per AC-test pair with explanation
  - Run as subagent call (isolated context, doesn't pollute main conversation)

### Tooling (Phase 3A scope)
- **`.agentic/lib/tools/spec-audit.sh`** — Verification mode only in this phase:
  ```bash
  bash spec-audit.sh                          # All shipped features
  bash spec-audit.sh F-XXXX                   # Single feature
  bash spec-audit.sh --since-last             # Changed since last audit
  bash spec-audit.sh --report                 # Full markdown report
  ```
- **`.agentic/lib/tools/test-review-prompt.md`** — LLM prompt template (as described above)
- **`.agentic/lib/tools/ag.sh`** — Add `ag audit` and `ag audit --full`
- Writes per-feature verification results to `.qa-tracker.json` (tracker created in 3C but verification writes to it)

## Phase 3B: Change Propagation Pipeline (F-XXXX) — Formal Only

**Goal**: Solve Problem 3 — when specs/NFRs change, trace the ripple effect and generate remediation plans.

### Change Propagation — "Is the Chain Still Intact?"

When something changes upstream, downstream artifacts go stale. This is a different problem from verification — verification asks "was it ever right?", propagation asks "is it *still* right after a change?"

**Trigger points** (when propagation check fires):

| Trigger | When | Scope |
|---------|------|-------|
| Migration created | `migration.sh create` | Features mentioned in migration |
| NFR modified | NFR.md changed (git diff) | All features referencing that NFR |
| Retrospective | Retro checklist | All features changed since last audit |
| Manual | `ag audit --propagate` | Configurable target |
| Feature completion | `ag done` | Just-shipped feature (quick structural check) |

**Dependency chain traced**:

```
NFR-0003 threshold changed (500ms → 200ms)
  └→ Which features reference NFR-0003? (grep FEATURES.md)
      ├→ F-0042: acceptance/F-0042.md NFR Compliance still says "< 500ms" ← STALE
      │   └→ tests/test_F0042_perf.py asserts < 500 ← STALE
      └→ F-0067: acceptance/F-0067.md says "< 200ms" ← OK
          └→ tests/test_F0067_perf.py asserts < 200 ← OK

Migration 009 (adds AC-003 to F-0055)
  └→ F-0055: New AC-003 "handles concurrent requests"
      └→ No test references AC-003 ← GAP
```

**Remediation output** — actionable work plan, not just a report:

```markdown
## Propagation Gaps — 3 items

### 1. F-0042: NFR-0003 criterion stale [BLOCKING]
- NFR-0003 threshold changed from 500ms → 200ms
- Acceptance file still says "< 500ms"
- Action: Update spec/acceptance/F-0042.md NFR Compliance section
- Action: Update test assertion in tests/test_F0042_response_time.py

### 2. F-0055: AC-003 has no test [MEDIUM]
- Migration 009 added AC-003 "handles concurrent requests"
- No test covers this
- Action: Write test for AC-003

### 3. F-0055: AC-001 test may not validate intent [REVIEW]
- LLM review: test asserts status 200 but AC says "returns paginated results"
- Action: Strengthen test assertions
```

The agent can `ag implement` each item, or the user batches them.

### Tooling (Phase 3B scope)
- **`.agentic/lib/tools/spec-audit.sh`** — Add propagation mode:
  ```bash
  bash spec-audit.sh --propagate NFR-0003      # Trace NFR change downstream
  bash spec-audit.sh --propagate migration:009  # Trace migration downstream
  ```
- **`.agentic/lib/tools/ag.sh`** — Add `ag audit --propagate <target>`
- **`.agentic/lib/tools/migration.sh`** — After `create`, auto-call `qa-tracker.sh add-propagation`
- **`.agentic/lib/tools/nfr.sh`** — After update, auto-call `qa-tracker.sh add-propagation`

## Phase 3C: QA Tracker State Machine (F-XXXX) — Formal Only

**Goal**: Persistent tracking with enforcement — every verification and propagation event is tracked, escalated, and visible.

### 3C: Tracking State Machine

The audit system isn't guidelines — it's a **tracked state machine** with persistent state, automatic work item creation, and visibility at every touchpoint.

**State file**: `.agentic/session/.qa-tracker.json` (gitignored, session-persistent)

```json
{
  "verification": {
    "last_full_audit": "2026-03-07T10:30:00Z",
    "last_audit_commit": "5295ffc",
    "audit_freshness_days": 30,
    "features": {
      "F-0148": {
        "last_verified": "2026-03-07T10:30:00Z",
        "commit_at_verify": "5295ffc",
        "structural": "pass",
        "coverage": "pass",
        "test_quality": "good",
        "llm_review": "pass"
      },
      "F-0042": {
        "last_verified": null,
        "structural": "unknown",
        "coverage": "unknown",
        "test_quality": "unknown",
        "llm_review": "unknown"
      }
    }
  },
  "propagation": {
    "pending": [
      {
        "id": "PQ-001",
        "created": "2026-03-07T11:00:00Z",
        "source": "NFR-0003",
        "change": "threshold 500ms → 200ms",
        "affected_features": ["F-0042", "F-0067"],
        "items": [
          { "feature": "F-0042", "artifact": "acceptance", "status": "open", "detail": "NFR Compliance still says < 500ms" },
          { "feature": "F-0042", "artifact": "test", "status": "open", "detail": "test asserts < 500" },
          { "feature": "F-0067", "artifact": "acceptance", "status": "resolved", "resolved_at": "2026-03-07T14:00:00Z" }
        ]
      }
    ],
    "resolved": [
      { "id": "PQ-000", "source": "migration:008", "resolved": "2026-03-06", "items_count": 2 }
    ]
  },
  "summary": {
    "features_total": 45,
    "features_verified": 38,
    "features_never_verified": 7,
    "pending_propagation_items": 3,
    "days_since_full_audit": 14,
    "audit_overdue": false
  }
}
```

**Key design**: every verification and propagation event mutates this state file. It's not a report you generate — it's a **living ledger**.

### 3D: Enforcement Points (where tracking has teeth)

The tracker surfaces at every touchpoint — not just "run ag audit sometime":

| Touchpoint | What's checked | Behavior |
|------------|---------------|----------|
| **Session start** | `ag audit --status` | Dashboard shows: "3 pending propagation items, 7 features never verified, audit overdue by 5 days" |
| **Pre-commit (advisory)** | Pending propagation count | Warning: "2 open propagation items from NFR-0003 change. Run `ag audit --propagate NFR-0003`" |
| **Feature completion** (`ag done`) | Quick chain check on shipped feature | Writes verification result to tracker. Warns if propagation items exist for this feature. |
| **Migration creation** | Auto-creates propagation items | `migration.sh create` → parses affected features → writes pending items to tracker. Not optional. |
| **NFR change** | Auto-creates propagation items | `nfr.sh` update → finds referencing features → writes pending items. Not optional. |
| **Retrospective** | Full audit + propagation sweep | Checklist won't complete until all BLOCKING propagation items are resolved or deferred with reason. |
| **`ag status`** | Summary line | Always shows: "QA: 38/45 verified, 3 pending items" (one-liner, always visible) |

**Escalation model** (not everything is blocking, but nothing is invisible):

```
Day 0:  Migration created → propagation items auto-created (INFO in session start)
Day 3:  Items still open → WARNING in session start dashboard
Day 7:  Items still open → WARNING in pre-commit output
Day 14: Items still open → BLOCKING in retro checklist (can't complete retro without addressing)
Day 30: Full audit overdue → WARNING at session start until audit runs
```

The escalation days are configurable in STACK.md:
```yaml
- qa_propagation_warn_days: 3
- qa_propagation_escalate_days: 7
- qa_audit_freshness_days: 30
```

## Risks

| Risk | Mitigation |
|------|------------|
| NFR Discovery adds ceremony to init | Discovery: optional guidelines, no formal linking. Formal: required but developer controls scope |
| LLM test review is token-expensive | Only runs during audit/retro, not pre-commit. `--since-last` scopes to changed features |
| Retro settings migration breaks existing projects | `retro_check.sh` supports both old and new format |
| Test quality heuristics produce false positives | Advisory only (exit 0 always), LLM review adds context |
| NFR catalog becomes stale | Retro workflow includes NFR coverage check, surfaces mismatches |
| First audit on mature project is overwhelming | Expected — it's a one-time review. Triage by severity (BLOCKING/MEDIUM/REVIEW) so user can prioritize |
| LLM review prompt needs calibration | First version ships, iterate based on real AC/test pairs. Version the prompt template for tuning |
