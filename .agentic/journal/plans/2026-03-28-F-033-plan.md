# Implementation Plan: F-033 "Project-Specific Customization Layer"

**Status**: APPROVED
**Feature**: F-033 — Project-Specific Customization Layer
**Date**: 2026-03-28

---

## 1. Title and Scope

**What F-033 delivers**: A structured, documented set of project-specific customization files that live in `.agentic/local/` (the upgrade-safe zone), allowing projects to define custom workflow steps, validation rules, enforcement policies, coding conventions, and Definition of Done criteria beyond what STACK.md settings can express. These customizations are consumed by framework scripts and agent instructions at clearly defined integration points.

**What F-033 explicitly does NOT deliver (boundary with F-034)**:
- **No automatic sync.** F-033 creates the customization files and their manual integration points. F-034 adds the auto-sync engine that detects when customization files change and regenerates framework artifacts.
- **No upgrade-time re-processing.** F-034 will re-process customizations into the new framework structure during upgrades. F-033 provides raw files and script integration only.
- **No conflict resolution.** F-034 handles "user customization vs. framework default" conflict resolution. F-033 uses a simple additive approach.

---

## 2. Current State Analysis

The framework already has several customization mechanisms via F-028 (shipped):

| Mechanism | Location | Status |
|-----------|----------|--------|
| Custom skills | `.agentic/local/extensions/skills/` | Wired into `generate-skills.sh` |
| Custom quality gates | `.agentic/local/extensions/gates/` | Wired into `pre-commit-check.sh` Check 17 |
| Custom rules | `.agentic/local/extensions/rules/` | Wired into `generate-skills.sh` |
| Custom hooks | `.agentic/local/extensions/hooks/` | **Scaffolded but NOT wired** (documented as "future") |

**Why F-033 is not F-028:**
F-028 delivered the **extension mechanism** — upgrade-safe directories and integration hooks for custom skills (copied by `generate-skills.sh`), custom gates (run by `pre-commit-check.sh` Check 17), and custom rules (injected into skills). F-033 delivers the **policy layer** — new customization dimensions that F-028's mechanism never addressed: project coding conventions, Definition of Done criteria, workflow phase directions, declarative enforcement policies, and wiring up F-028's scaffolded-but-inert lifecycle hooks directory. Without F-033, projects can extend skills and add pre-commit gates, but cannot customize the framework's workflow behavior, completion criteria, or coding standards in an upgrade-safe way.

**Key gaps F-033 fills:**
1. **No custom Definition of Done** — `feature-complete.sh` has hardcoded checks only
2. **No custom coding conventions** — `conventions.md` is a framework file overwritten on upgrade
3. **No custom workflow phase directions** — role prompts are framework files
4. **No lifecycle hooks integration** — hooks directory exists but nothing reads from it
5. **No custom enforcement policies** — beyond STACK.md on/off switches

---

## 3. Approach

**Design philosophy**: Extend the existing `.agentic/local/extensions/` pattern (F-028) rather than creating a parallel system.

**Key architectural decisions:**
1. **Files live in `.agentic/local/`** (upgrade-safe, established by F-028)
2. **Integration via scripts, not behavioral instructions** (principle D2: Deterministic Enforcement)
3. **Additive, not replacement** — custom checks ADD to framework checks, never replace them
4. **Live reading for agent-consumed files; script processing for enforcement files**

---

## 4. Implementation Phases

### Phase 1: Custom Conventions File

Allow projects to declare coding conventions that supplement `conventions.md`.

**New file**: `.agentic/lib/init/conventions-local.template.md` — template with commented-out examples
**Integration**:
- `.agentic/conventions.md` — add pointer section to `local/conventions.md`
- `.agentic/prompts/implementer.md` — add local conventions reference
- `.agentic/lib/init/scaffold.sh` — create local conventions from template during init

### Phase 2: Custom Definition of Done

Allow projects to add custom checks to feature completion validation.

**New directory**: `.agentic/local/extensions/done-checks/` — bash scripts (same pattern as `gates/`)
- Each script receives `$1` = feature_id, exits 0 (pass) or 1 (fail)
- Naming convention: `NNN-description.sh` (ordering number prefix)

**Integration**:
- `.agentic/lib/hooks/feature-complete.sh` — after hardcoded checks, scan `done-checks/` and execute in sort order
- `.agentic/lib/init/scaffold.sh` — create `done-checks/` directory

### Phase 3: Custom Lifecycle Hooks (completes F-028's scaffolded hook infrastructure)

Wire up the existing but inert `.agentic/local/extensions/hooks/` directory.

**Hook points**: `after-implement.sh`, `after-commit.sh`, `after-done.sh`, `before-plan.sh`

**Integration**:
- `.agentic/lib/tools/commands/operations.sh` — at end of `cmd_implement`, `cmd_commit`, `cmd_done`, check for and execute corresponding hook
- Hooks run with `set +e` — warn on failure but do not block the command

### Phase 4: Custom Workflow Phase Directions

Allow projects to inject custom instructions at specific workflow phases.

**New template**: `.agentic/lib/init/workflow-directions.template.md`
**File**: `.agentic/local/workflow-directions.md` (user-created from template)
- Sections keyed by phase: `## Planning`, `## Implementation`, `## Verification`, `## Review`

**Integration**:
- `.agentic/lib/tools/commands/operations.sh` — after printing playbook references, cat relevant section from `workflow-directions.md`

### Phase 5: Custom Enforcement Policies

Allow projects to define custom pre-commit enforcement rules via YAML policy files.

**New directory**: `.agentic/local/extensions/policies/` — YAML files with `name`, `check`, `severity`, `message`

**Integration**:
- `.agentic/lib/hooks/pre-commit-check.sh` — after check 17 (custom gates), add policy evaluation loop
- Malformed YAML is skipped with warning, never breaks framework gates

### Phase 6: Documentation and Validation

- `tests/validate_framework.sh` — add F-033 structural tests
- `.agentic/lib/init/extensions-readme.md` — comprehensive documentation of all extension points
- `.agentic/lib/DEVELOPER_GUIDE.md` — add "Project Customization" section
- `CONTEXT_PACK.md` — update architecture snapshot

## 6. Risks and Mitigations

| Risk | Severity | Mitigation |
|------|----------|------------|
| Custom gates/policies slow pre-commit | Medium | Timeout each custom script (3s max) |
| Malformed YAML in policies/ crashes pre-commit | High | Wrap YAML parsing in try/catch, skip malformed, continue |
| Bad lifecycle hooks break `ag` commands | Medium | Hooks run with `set +e`, warn but don't block |
| Token bloat from custom conventions | Low | Document size limits in template |
| Confusion between framework and local conventions | Medium | Clear naming, explicit cross-references |

## 7. Open Questions

1. **Pointer vs. copy for conventions?** Live reading (pointer) is simpler; copying during `generate-skills.sh` is more deterministic. **Recommendation**: Pointer for F-033, F-034 can add copy/merge.

2. **Should custom DoD checks be able to REPLACE framework checks?** **Recommendation**: Additive only. `custom_dod_mode: replace | extend` can be added later if needed.

3. **Single file vs. separate files for workflow directions?** **Recommendation**: Single file with sections (small, <100 lines).

4. **Complex rule engine for policies?** **Recommendation**: Start simple — one `check` command per policy. Complex rules go in `gates/` as bash scripts.

## 8. Testing Strategy

**Structural tests** (validate_framework.sh):
- Template files exist
- `scaffold.sh` creates all extension directories
- Integration code exists in `feature-complete.sh`, `pre-commit-check.sh`, `operations.sh`

**Integration tests** (manual, scratch project):
1. Scaffold → verify directories created
2. Custom gate → verify it runs at pre-commit
3. Custom done-check → verify it runs at `ag done`
4. Policy YAML → verify evaluation at pre-commit
5. Lifecycle hook → verify firing at `ag commit`
6. Malformed YAML → verify graceful degradation
7. Failing hook → verify warning without blocking
