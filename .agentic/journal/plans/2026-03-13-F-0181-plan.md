# Plan Review: F-0181 Autonomous Formal Profile

## Review Summary

The plan covers the core idea well and correctly identifies the main files. However, it **significantly underestimates the number of hardcoded profile validation sites** across the codebase, **makes a dangerously wrong claim about upgrade.sh being data-driven**, and **misses a structural problem in scaffold.sh** where `autonomous_formal` would silently take the wrong init path. There are also ADR table discrepancies.

---

## Findings

### [CRITICAL] C1: scaffold.sh has profile-as-control-flow — `autonomous_formal` would get Discovery init path

**scaffold.sh line 280**: `if [[ "${PROFILE}" == "discovery" ]]` does an early exit with discovery-specific setup. Line 331 onward is the "formal path" (creates spec dirs, TECH_SPEC.md, FEATURES.md, git hooks, pipeline infrastructure).

The plan says to update the case-statement validation (line 64), but **does not address the branching logic on lines 280-329**. With the plan's changes, `autonomous_formal` would:
1. Pass validation (line 64: `discovery|formal|autonomous_formal`)
2. Hit the `if [[ "${PROFILE}" == "discovery" ]]` check on line 280 — this is FALSE
3. Fall through to the formal path (lines 331+) — **this happens to be correct behavior**

Wait — on closer inspection, this actually works by accident because anything not `discovery` falls to the formal path. BUT there is still a problem:

- **Line 241**: `[[ "$file_profile" == "formal" && "$PROFILE" != "formal" ]] && continue` — This skips formal-only state files when profile is NOT "formal". For `autonomous_formal`, this will **skip all formal-only files** (FEATURES.md, ISSUES.md, LESSONS.md, NFR.md, REFERENCES.md, acceptance/README.md). The `autonomous_formal` profile should get these files since it inherits Formal's full rigor.

- **Line 258**: `sed ... "s/...\1${PROFILE}  # discovery | formal/"` — hardcoded comment will be stale.

This is a correctness bug: `autonomous_formal` would initialize without spec files.

### [CRITICAL] C2: `state-files.conf` uses `formal` as a gate — `autonomous_formal` excluded

In `state-files.conf`, lines 15-20 mark files with `:formal` profile. The gating logic in both `scaffold.sh` (line 241) and `verify.py` (line 35) and `upgrade.sh` (line 407) all use:
```
file_profile == "formal" and profile != "formal" → skip
```

This means `autonomous_formal` would:
- NOT get FEATURES.md, ISSUES.md, LESSONS.md, NFR.md, REFERENCES.md, acceptance/README.md during init
- NOT get these files during upgrade
- NOT be flagged as missing them during verify

The plan doesn't mention this at all. Fix requires either:
- (a) Changing the gate to `profile not in ("formal", "autonomous_formal")` in 3 files + state-files.conf to add `autonomous_formal` entries
- (b) Changing state-files.conf to use a `structured` marker and updating the gate logic
- (c) Adding a helper function `is_formal_like(profile)` used everywhere

### [CRITICAL] C3: `settings.py` `_resolve_profile()` rejects `autonomous_formal`

Lines 148 and 153 of `settings.py`:
```python
if raw.lower() in ("discovery", "formal"):
    return raw.lower()
```

The plan correctly identifies this (Section 2, bullet 4: update tuple). But the plan says to update "lines 148, 153" — this is **two separate checks** in `_resolve_profile()`. If either is missed, `autonomous_formal` in STACK.md would be silently ignored and profile would fall through to inference (defaulting to `discovery` or `formal` based on directory structure). This is a silent data loss bug.

### [CRITICAL] C4: `settings.sh` `_get_profile()` also rejects `autonomous_formal` — MISSED BY PLAN

The plan lists 4 validation locations. It **completely misses** `settings.sh` lines 123 and 133:
```bash
case "$val" in
    discovery|formal) _SETTINGS_PROFILE_CACHE="$val" ;;
    *) _SETTINGS_PROFILE_CACHE="" ;;
esac
```

This is the **shell equivalent** of settings.py's _resolve_profile. It's used by `ag.sh` and every shell script that sources `settings.sh`. If not updated, `autonomous_formal` would be silently rejected by all shell-based tooling even after `ag set profile autonomous_formal` writes it to STACK.md.

This is arguably the most dangerous miss — the profile would be set in STACK.md but never actually read back.

### [HIGH] H1: upgrade.sh is NOT "data-driven" for profile resolution — Plan claim is wrong

The plan states (Section 6): "No code changes needed — upgrade.sh is already data-driven (loops profiles.conf)."

This is **incorrect**. While upgrade.sh does loop profiles.conf for settings injection (lines 588-619), it also has:

1. **Line 335-337**: Hardcoded profile detection:
   ```bash
   case "$PROFILE_LINE" in
       *core+product*|*core+pm*) PROFILE="formal" ;;
       *formal*) PROFILE="formal" ;;
   esac
   ```
   `autonomous_formal` would match `*formal*` — this accidentally works but is fragile.

2. **Line 407**: `[[ "$file_profile" == "formal" && "$PROFILE" != "formal" ]] && continue` — same `state-files.conf` gating bug as C2. If the profile is detected as `autonomous_formal`, formal-only state files are skipped during upgrade.

3. **Line 564**: Settings block substitution loops profiles.conf — this part IS data-driven. But only for settings injection, not for file creation.

AC-003 is NOT satisfied by "existing upgrade.sh logic + new profiles.conf entry" as the plan claims.

### [HIGH] H2: `discover.py` and `render_proposals.py` have hardcoded `choices=["discovery", "formal"]` — MISSED BY PLAN

- `discover.py` line 1434: `choices=["discovery", "formal"]`
- `render_proposals.py` line 403: `choices=["discovery", "formal"]`

These are argparse validators. Running `discover.sh --profile autonomous_formal` would fail with an argparse error. The plan does not list these files.

### [HIGH] H3: `discover.sh` usage text has hardcoded profile list — MISSED BY PLAN

Line 30: `echo "Usage: bash .agentic/tools/discover.sh [--profile discovery|formal] [--root DIR]"`

### [HIGH] H4: `continue_here.py` binary profile mapping breaks — needs update

Line 147: `return "Formal" if profile == "formal" else "Discovery"`

With `autonomous_formal`, this returns "Discovery" — incorrect. Should return "Formal" or a new label.

### [HIGH] H5: `enable-formal.sh` should probably be aware of `autonomous_formal`

This script (line 47) checks `if [[ "$CURRENT_PROFILE" == "formal" ]]` to detect if formal is already enabled. If a user is on `autonomous_formal` and runs `enable-formal.sh`, it would:
- Not recognize it's already a formal-like profile
- Downgrade settings by switching to `formal`

Should either warn or be generalized to `enable-formal-like.sh`.

### [HIGH] H6: ADR table vs. plan's review defaults table — non-review settings are underspecified

The plan says "All non-review settings: (same as formal)". But it doesn't specify what those values actually ARE. This is important because:

- Should `autonomous_formal` inherit `formal`'s `max_files_per_commit: 10`? Or have its own limits?
- Should `autonomous_formal` inherit `formal`'s `git_workflow: pull_request`? (This seems right — "merge still requires human")
- Should `autonomous_formal` get `plan_review_enabled: yes`? (If yes, but review_plan is `critical_agent`, that creates an auto-reviewed plan loop — is that intentional?)

This should be explicit in the plan to avoid ambiguity during implementation.

### [MEDIUM] M1: STACK.template.md review checkpoint comments only show Discovery/Formal

Lines 71-85 show comments like:

These need updating to include Autonomous Formal values, e.g.:
```
# planned -> specced. Discovery: auto | Formal: critical_agent | Autonomous Formal: critical_agent
```

The plan mentions this (Section 3) but is vague: "add `Autonomous Formal: critical_agent`". Should be explicit about all 8 checkpoints.

### [MEDIUM] M3: `agent_operating_guidelines.md` says "only these two" — MISSED

### [MEDIUM] M4: `constraints.conf` may need new rules

But since profile resolution resolves these from profiles.conf, constraint validation would work IF settings.py resolves the profile correctly (see C3).

No new constraints needed, but worth verifying the constraint engine handles the new profile.

## Verdict

**Do not implement as-is.** The plan has 4 CRITICAL findings that would result in a non-functional profile:

1. settings.sh completely missed — profile would never be read back by shell scripts
2. state-files.conf gating would skip all formal-only files for the new profile
3. The "upgrade.sh needs no changes" claim is wrong
4. scaffold.sh state-file gating would produce an incomplete project

Recommend revising the plan to:
- Add a helper function `is_structured_profile()` (or equivalent) that returns true for both `formal` and `autonomous_formal`, used in all gating logic
- Enumerate ALL 18 files needing changes
- Add negative and round-trip tests
- Explicitly list all 30 profiles.conf settings for the new profile (not just "same as formal")
