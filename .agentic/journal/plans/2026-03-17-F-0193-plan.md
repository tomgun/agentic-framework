# F-0193: Centralized & Future-Proof Feature IDs

**Status**: APPROVED

## Context

Feature IDs (`F-XXXX`) use zero-padded 4-digit sequential numbers assigned at spec time. Three problems:
1. **Implied ordering** — backlog items have lower numbers than recently shipped features, which looks confusing
2. **Hard ceiling** — `\d{4}` regex breaks at F-10000
3. **Multi-agent collision** — two agents independently pick "next ID" and get the same number

The ID pattern is duplicated in **100+ locations** across ~50 files. Any format change today touches every one of them. The key insight: **centralize first, then any future format change is a one-file edit**.

Also resolves: T-0045 (collision-proof ID research).

## Design Decisions

### Format: Widen to `\d{4,}`, keep zero-padding for existing range

```python
def format_feature_id(n: int) -> str:
    return f"F-{n:04d}" if n < 10000 else f"F-{n}"
```

New IDs still look like F-0234 through F-9999. At F-10000 the padding naturally drops.

**Why keep zeros for now?**
- 233 existing IDs in filenames, git history, plans, journals — changing them breaks grep
- `F-0042` sorts correctly before `F-0193` as a string; `F-42` wouldn't
- The user's question "why leading zeros?" — answer: sortable filenames and historical consistency. The plan removes the ceiling so they don't create a hard limit.

**What about the ordering concern?**
Sequential IDs inherently encode creation order. This plan doesn't change that — and that's intentional. The centralization makes future format changes (random IDs, hash-based, allocation-at-implementation) a single-file edit. If ordering proves to be a real problem beyond aesthetics, the infrastructure is ready. The existing backlog (BACKLOG.json) already provides explicit priority ordering independent of ID numbers.

**Why not random alphanumeric (F-k7m2x)?**
- Destroys sortability in file listings
- Harder to type/speak ("feature k7m2x" vs "feature 234")
- This plan supersedes the epic plan's hash approach (`F-[a-f0-9]{5,8}`) with the simpler `\d{4,}` widening

**Collision prevention — deferred:**
The current code (epic.py:557) notes: "not atomic — acceptable because callers are human-gated." Both reviewers agree `fcntl.flock` adds complexity for a race condition that hasn't occurred. Centralization enables adding locking later in one place if multi-agent parallel allocation (e.g., via coord server F-0230) becomes real.

### Scope: Feature IDs (F-XXXX) only in PR 1

Other ID types (NFR, T, I, HN, FB, R) have the same ceiling problem but are lower priority. Defer to a follow-up PR to keep blast radius manageable.

#### Step 2: Create `/.agentic/lib/ids.sh` + shell function

Instead of a bare variable (which has context-dependent expansion issues in grep vs `=~` vs case), provide a **shell function**:

```bash
#!/usr/bin/env bash
# ids.sh — Centralized ID patterns for shell scripts

# ERE pattern (for grep -E)
FEATURE_ID_ERE='F-[0-9]{4,}'
FEATURE_ID_ERE_ANCHORED='^F-[0-9]{4,}$'
FEATURE_HEADER_ERE='^## F-[0-9]{4,}:'

# Shell function — works in all contexts
is_feature_id() {
    [[ "$1" =~ ^F-[0-9]{4,}$ ]]
}
```
